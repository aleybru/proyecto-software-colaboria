## Objetivo

Convertir la sala ya usable de TASK-0020 en una **sala real**: Papu responde mediante OpenAI y Chapu mediante Anthropic, usando las credenciales ya configuradas, sin agregar todavía Source Registry, Drive/repo retrieval, tools ni gateway. El objetivo de esta tarea es que Dani pueda empezar a usar ColaborIA de verdad ahora.

## Qué tiene que hacer Code (concreto)

### 1. Reemplazar el adapter fake por ejecución real, sin tocar routing/floor

Mantener `ConversationOrchestrationService` como único dueño de routing, floor lock, orden `papu -> chapu`, idempotencia y lifecycle de ronda.

Refactor mínimo del contrato `IAgentAdapter` para que reciba un request de ejecución ya resuelto por backend (agente + provider/model + contexto exacto) y devuelva `Succeeded | Failed | TimedOut`. El adapter **no** recibe `DbContext`, `ConversationRound` ni permisos para decidir routing.

Conservar `DeterministicFakeAgentAdapter` para tests automáticos. En ejecución normal de la app, registrar un adapter real que despache según el `runtime_binding` del agente:

- `openai` -> Papu;
- `anthropic` -> Chapu.

El modelo se toma exactamente de `AgentRegistry`/`runtime_binding`. **No hacer fallback silencioso a otro modelo.** Si el proveedor rechaza el modelo configurado, devolver error tipado y documentarlo; cualquier cambio de `config/agents/*.yml` requiere decisión explícita posterior.

### 2. Reusar las API keys existentes

Usar las credenciales globales `openai/api_key` y `anthropic/api_key` ya implementadas y verificadas por TASK-0006, a través de la infraestructura de cifrado existente.

Nunca loguear ni persistir la key en texto plano. No agregar una segunda fuente de credenciales.

Implementar llamadas reales a las APIs vigentes de OpenAI y Anthropic con `HttpClient`/SDK según convenga, con timeout explícito y sin streaming en esta tarea.

### 3. Contexto mínimo pero reconstructible

Antes de cada llamada real crear un **snapshot durable del input exacto** enviado al proveedor y usarlo como `agent_turn.input_context_ref`.

No construir todavía un Context Builder general. Para TASK-0021 el contexto entregado es deliberadamente mínimo y debe contener solamente:

- identidad del proyecto (`project_id`, nombre, tipo);
- `agent_id`, `definition_hash` e instrucciones exactas del perfil cargado;
- provider/model exactos usados;
- transcript necesario de la sesión, en el mismo orden enviado al proveedor;
- para el segundo turno de `both_sequential`, el mensaje real persistido del primer agente.

Persistir un objeto/tabla equivalente a `context_snapshots` con, como mínimo:

- `id` (`Guid`);
- `project_id`;
- `session_id`;
- `agent_id`;
- `agent_definition_hash`;
- `provider`;
- `model`;
- `request_payload` (JSON/texto con el **body exacto enviado al proveedor, sin headers/secretos**);
- `payload_sha256`;
- `created_at`.

`agent_turn.input_context_ref` debe apuntar al snapshot real creado para ese turno. No placeholders. Debe ser posible releer el snapshot y verificar su hash.

**Fuera de esta tarea:** protocolo completo, Decisions, Drive, repo, Source Registry y recuperación de fuentes. No inventar ni simular esas fuentes. El snapshot registra sólo lo que efectivamente se envió.

### 4. Errores reales de proveedor

Mapear como mínimo a resultados trazables sin romper la sala:

- credencial ausente/revocada;
- autenticación rechazada;
- modelo/request no soportado;
- rate limit;
- timeout;
- error de red/proveedor;
- respuesta inválida/vacía.

Ante fallo/timeout:

- no crear `message` de agente;
- `agent_turn` queda `Failed` o `Timeout` con detalle seguro;
- la ronda termina `Stopped`;
- en `both_sequential`, si Papu falla, Chapu no arranca;
- el floor siempre se libera mediante el lifecycle ya implementado.

No exponer cuerpos completos de error del proveedor si pudieran contener datos sensibles. Conservar request-id/provider metadata cuando sea segura y útil para diagnóstico.

### 5. UI mínima para modo real

Reusar `features/room`; no rediseñar la sala.

Cambios mínimos:

- retirar el banner "Modo de prueba — respuestas determinísticas" cuando el backend está usando providers reales;
- mostrar de forma discreta que la respuesta proviene del agente real y, si ya está disponible en la respuesta/metadata, provider/model;
- mantener los estados UX existentes y sumar mensajes claros para `provider_error`, `rate_limited`, `timeout`, `credential_missing/invalid` y `model_unavailable` (nombres exactos pueden adaptarse al contrato backend existente);
- no agregar streaming, configuración avanzada ni paneles nuevos.

### Backend

- **`IAgentAdapter` refactorizado** (TASK-0019 → TASK-0021): `BuildRequestPayload(AgentExecutionRequest)`
  puro (sin red ni DB) construye el payload exacto; `ExecuteAsync(request, requestPayload, ct)`
  recibe ESE MISMO string y lo envía tal cual — garantiza que lo persistido en el snapshot y lo
  realmente enviado al proveedor sean idénticos byte a byte, sin reconstrucción separada.
  `AgentExecutionRequest` es un record con todo lo ya resuelto por el orquestador (proyecto,
  agente, `definition_hash`, instructions, provider/model exactos, transcript en orden) — el
  adapter sigue sin `DbContext`/`ConversationRound`/capacidad de routing, verificado por
  reflexión en `IAgentAdapterContractTests` (actualizado para el nuevo contrato: ahora también
  cubre `BuildRequestPayload` y valida que ninguna propiedad de `AgentExecutionRequest` sea un
  tipo de persistencia).
- **`ContextSnapshot`** (migración `AddContextSnapshots`, tabla `context_snapshots`): `id`,
  `project_id`, `session_id`, `agent_id`, `agent_definition_hash`, `provider`, `model`,
  `request_payload` (body exacto, sin headers/secretos), `payload_sha256`, `created_at`. Se crea
  **antes** de cada llamada real, con su propio `SaveChangesAsync`. `AgentTurn.InputContextRef`
  pasa de `string?` (placeholder de TASK-0018, nunca poblado hasta ahora) a `Guid?` real, FK a
  `context_snapshots` (`ON DELETE CASCADE`). Contexto V0 deliberadamente mínimo: identidad de
  proyecto, `agent_id`/`definition_hash`/instructions exactas, provider/model exactos, y el
  transcript aplanado a turnos `user`/`assistant` (mensajes propios previos del agente →
  `assistant`; cualquier otro mensaje, incluido el del otro agente en `both_sequential` →
  `user`, prefijado `"Dani: ..."`/`"Papu: ..."`/`"Chapu: ..."` para atribución). Sin Source
  Registry, Drive/repo ni Decisions — nada de eso se simula.
- **`RealAgentAdapter`**: llamadas HTTP reales a `api.openai.com/v1/chat/completions` (Bearer) y
  `api.anthropic.com/v1/messages` (`x-api-key` + `anthropic-version`), timeout explícito de 60s
  (`HttpClient` nombrado `"LlmReal"`, DEC-C08 — criterio de Code, generoso respecto de los
  timeouts de ronda/turno ya existentes desde TASK-2019/2020), sin streaming. Modelo tomado
  exacto de `AgentRegistry`/`runtime_binding` (`papu.yml` → `gpt-5.1`, `chapu.yml` →
  `claude-sonnet-5`) — **no se tocó ninguno de los dos YAML** en ningún momento, ni siquiera
  durante la investigación del bloqueo real descripto más abajo. `LoadApiKeyAsync` reusa
  exactamente el mismo patrón de `LlmKeyValidationService` (TASK-0006): busca la credencial
  global activa por proveedor y la descifra a una variable local, nunca logueada ni persistida.
  Taxonomía de error tipada con prefijo estable antes de `:` — `credential_missing`,
  `credential_invalid` (401/403), `rate_limited` (429), `model_unavailable` (400/404/422),
  `provider_error` (5xx/red), `invalid_response` (200 sin contenido interpretable), `timeout`
  (vía `catch (OperationCanceledException) when (!cancellationToken.IsCancellationRequested)`,
  distinguiendo el timeout propio del `HttpClient` de una cancelación real del caller). Nunca se
  expone el cuerpo crudo del proveedor — sólo un resumen (`error.message` si el proveedor lo dio)
  + el status code.
- **`ConversationOrchestrationService.RunSingleTurnAsync`**: arma el `AgentExecutionRequest`,
  pide el payload al adapter, persiste el `ContextSnapshot`, arranca el turno con
  `inputContextRef` real, y sólo entonces llama a `ExecuteAsync`. Ante `TimedOut`, el detalle
  seguro del error ahora también se guarda en `agent_turn.error` (antes sólo pasaba con
  `Failed`). `RunAndFinalizeAsync` devuelve el `detail` del turno no exitoso cuando la ronda
  termina `Stopped`, y ese detalle (con su prefijo tipado) se propaga tal cual hasta la respuesta
  HTTP de `SendAsync`/`StartRoundAsync` — sin vocabulario de wire nuevo más allá de lo que
  `detail` ya transportaba desde TASK-0020.

### Limitación real encontrada — bloqueante, reportada a Dani durante la ejecución

Durante la verificación en vivo, **tanto la cuenta de OpenAI como la de Anthropic configuradas
para ColaborIA devolvieron error real por saldo/crédito agotado**:

- OpenAI, HTTP 429: *"You have no credits remaining. Add credits to continue using the API..."*
- Anthropic, HTTP 400: *"Your credit balance is too low to access the Anthropic API..."*

Las credenciales en sí son válidas (`status: valid` en ambos casos) — el problema es de
facturación de la cuenta, no de código ni de configuración. Esto **confirmó el camino de fallo
real de punta a punta** (sin mensaje fantasma, sin floor trabado, ronda `Stopped` con detalle
seguro tipado — de hecho una evidencia más fuerte que un fallo sintético, porque ocurrió
orgánicamente contra la API real) pero **impidió confirmar una respuesta real exitosa de
cualquiera de los dos proveedores**, y por lo tanto también impidió confirmar si `gpt-5.1`
(modelo configurado para Papu) es un modelo válido/habilitado — la llamada falla en facturación
antes de llegar a validar el modelo, así que esto queda **no verificado, no refutado**.

Reportado a Dani en el momento (vía pregunta directa durante la ejecución). Dani agregó crédito a
ambas cuentas; se reintentó con llamadas de bajo costo cada vez con backoff creciente (20s → 3min
→ 5min → 15min → 25min, ~50 minutos totales, 7 intentos) sin que el saldo propagara del lado de
ninguno de los dos proveedores. Ante la persistencia del bloqueo, se decidió junto con Dani
documentar esto como limitación real conocida y cerrar la tarea en este estado — el código, la
infraestructura de contexto/snapshot, y el manejo de errores están completos y verificados por el
camino de fallo real; sólo falta la confirmación en vivo de una respuesta real exitosa cuando
haya saldo. No se modificó `config/agents/*.yml` en ningún momento para evitar o enmascarar este
bloqueo.

**Pendiente para cuando haya saldo real en ambas cuentas** (no requiere ningún cambio de código,
sólo re-ejecutar la verificación en vivo ya escrita): confirmar una respuesta real exitosa de
Papu y de Chapu; confirmar `both_sequential` con Chapu recibiendo en su contexto el mensaje real
ya persistido de Papu (criterio #4); y, de paso, confirmar si `gpt-5.1` es aceptado por OpenAI o
si hace falta una decisión explícita de Dani para cambiar el modelo de Papu.
