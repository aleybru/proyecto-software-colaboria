## Objetivo

**Nota de trazabilidad:** reconstrucción retrospectiva, escrita el 2026-08-30. Identificada en los commits del repo de código como **"TASK-0013"** — se conserva ese ID histórico como alias; el ID canónico en `code-tasks/` es **TASK-0014**.

Resolver el bloqueo real de creación de repos de GitHub en cuenta personal (`aleybru`), encontrado durante TASK-0008/TASK-0010 (cancelada). Causa exacta identificada: `CreateRepositoryAsync` generaba un installation access token (server-to-server) y llamaba a `POST /orgs/{owner}/repos` — endpoint que solo existe para organizaciones. La conclusión anterior ("GitHub no permite crear repos en cuentas personales") era del endpoint equivocado, no una limitación real de GitHub.

## Qué se hizo (reconstruido de la evidencia real)

Confirmado contra documentación oficial de GitHub antes de implementar: para cuentas personales, `POST /user/repos` es el endpoint soportado, y exige un **GitHub App user access token** (flujo de user authorization, similar a OAuth), no un installation token.

**Backend:**
- Nuevo flujo de user authorization en `GitHubAppService` (mismo mecanismo que Google Drive de TASK-0012): `BuildUserAuthorizationUrlAsync`/`HandleUserAuthorizationCallbackAsync`, reutilizando `OAuthStateStore`.
- Nuevos tipos de credencial: `oauth_client_config` (Client ID/Secret/redirect) y `user_authorization` (refresh token o access token directo — nunca el token efímero de instalación; autenticación de instalación y de usuario se mantienen conceptualmente separadas).
- `CreateRepositoryAsync` reescrito: usa el user access token contra `POST /user/repos` (con `GET` previo para idempotencia), y solo marca `active` después de verificar con un installation token que la GitHub App puede leer el repo recién creado.
- Caso documentado, no resuelto con PAT: si la instalación es "selected repositories" y no incluye el repo nuevo, se informa `github_repo_created_but_app_access_missing` en vez de asumir éxito o introducir un PAT — el único endpoint documentado para agregarlo (`PUT /user/installations/{id}/repositories/{repo_id}`) exige explícitamente un PAT clásico según GitHub, y se descartó usarlo.
- Endpoints nuevos: `POST /integrations/github-app/oauth-config`, `GET /integrations/github-app/authorize`, `GET /integrations/github-app/callback`.
- Estados nuevos en `ProjectResource.Status`: `github_user_authorization_required`, `github_repo_created_but_app_access_missing`, `github_repo_creation_failed`, `active`.

**Frontend:**
- Nuevo `core/github-app.ts` (mismo patrón que `google-drive.ts`).
- `project-detail`: botón "Autorizar GitHub" cuando el estado es `github_user_authorization_required`, mismo tratamiento que "Reconectar Google Drive". `narrative` nunca ofrece ninguna acción de GitHub. Sin formulario nuevo en `/projects/new`.
