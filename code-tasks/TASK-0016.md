## Objetivo

Implementar la primera capa del Bloque C de DEC-C16: definiciones de agente versionadas (`config/agents/papu.yml`, `config/agents/chapu.yml`), un `AgentRegistry` que las carga y valida al arrancar el backend, y un endpoint de solo lectura para verificar qué se cargó. **Sin llamadas reales a OpenAI/Anthropic, sin Context Builder, sin sala/chat, sin gateway de recursos, sin permisos Drive/GitHub, sin ejecución autónoma** — eso es alcance de tareas posteriores.

## Qué tiene que hacer Code (concreto)

1. Definir el schema/modelo común, con dos secciones estructuralmente separadas dentro del mismo archivo YAML:

   **`AgentDefinition`** (identidad, relativamente estable):
   - `id` (string, inmutable una vez usado — identidad lógica del agente, no cambia aunque cambien instrucciones o modelo)
   - `display_name`
   - `role_summary` (texto corto, seguro de exponer públicamente)
   - `skills` (lista — deliberadamente `skills`, no `capabilities`, para no confundir habilidad declarada con autorización efectiva)
   - `instructions` (texto completo — **nunca** se expone por API)
   - `schema_version` (versión del formato del YAML en sí)
   - `status` (`active` | `deprecated`)

   **`RuntimeBinding`** (puede cambiar sin que cambie la identidad):
   - `provider` — valores canónicos alineados con los ya existentes en `credentials` (TASK-0006): `openai` | `anthropic`.
   - `model` (string, no vacío).

2. Crear `config/agents/papu.yml` (provider: `openai`) y `config/agents/chapu.yml` (provider: `anthropic`), con contenido real (no placeholder) para `role_summary` y `skills`, coherente con los perfiles ya descritos en el protocolo común y en `project.yml` (`rol_papu_en_este_proyecto` / `rol_chapu_en_este_proyecto`).

3. Calcular `definition_hash`: SHA-256 sobre la definición normalizada (identidad + runtime binding, forma canónica estable ante reordenamiento de campos/espacios). **No usar un contador manual como mecanismo de trazabilidad.** Este hash es lo que cambia cuando cambian instrucciones o modelo — el `id` no cambia.

4. Implementar `AgentRegistry` en el backend:
   - carga y valida los YAML al startup;
   - mantiene las definiciones cargadas en memoria después del arranque;
   - **no implementar aliases** (fuera de alcance de esta tarea).

5. Validaciones al cargar, y comportamiento ante fallo — **fail closed, no fail down**:
   - rechazar: ID duplicado, YAML inválido, campos obligatorios faltantes, `provider` fuera de los valores canónicos soportados, `model` vacío;
   - **no** validar contra red si el modelo existe realmente en el proveedor — alcanza con `provider` soportado + `model` no vacío; la validación real contra el proveedor corresponde al adapter/runtime de una tarea posterior;
   - si la carga falla, el `AgentRegistry` queda en estado `unavailable`/`degraded` — **el resto de la aplicación sigue operativo** (Bloque B — proyectos y aprovisionamiento no debe verse afectado). Los endpoints que dependan de agentes deben rechazar con un estado tipado y explicable, no con una caída genérica de la API.

6. Endpoint `GET /agents` (solo lectura, para verificación):
   - devuelve únicamente metadata segura: `id`, `display_name`, `role_summary`, `provider`, `model`, `schema_version`, `definition_hash`, `status`;
   - **nunca** devuelve `instructions`;
   - si el registro está `unavailable`/`degraded`, el endpoint lo refleja explícitamente en vez de devolver una lista vacía sin explicación.

## Criterio de éxito

- Con `papu.yml` y `chapu.yml` válidos, el backend arranca normalmente y `GET /agents` devuelve ambos perfiles con metadata correcta — sin `instructions` en la respuesta, verificable inspeccionando el JSON completo.
- `definition_hash` de cada agente es determinístico: cargar el mismo YAML dos veces produce el mismo hash; cambiar una coma o el orden de un campo no cambia el resultado *sustantivo* si el contenido normalizado es el mismo (si cambia el contenido real, sí debe cambiar el hash).
- Provocar cada uno de los errores de validación (ID duplicado entre los dos YAML, campo obligatorio faltante, `provider` inválido, `model` vacío) y confirmar que el registro queda `unavailable`/`degraded`, con el motivo específico visible — no un error genérico.
- Con el registro en estado `unavailable`/`degraded` por un YAML roto, confirmar que un endpoint no relacionado con agentes (ej. `GET /projects`, de TASK-0007/0012) sigue respondiendo con normalidad.
- Un endpoint que dependa de agentes (puede ser el propio `GET /agents` en su variante de error) responde con un estado tipado y explicable cuando el registro está degradado, no con un 500 sin contexto.

## Contexto / restricciones

- No implementar Context Builder, sala/chat, gateway de recursos, permisos Drive/GitHub, ni ejecución autónoma — eso es alcance de Bloque D/E (tareas posteriores).
- No implementar aliases de agente.
- No validar `model` contra la API real del proveedor.
- No es necesario `created_at`/`updated_at` en el YAML — el historial de cambios ya lo sostiene git.
- Respetar DEC-C08: detalles técnicos menores (forma exacta de la normalización previa al hash, estructura interna del registro en memoria) quedan a criterio de Code, documentados en `## Resultado`.
